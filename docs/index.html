The problem

Phishing works because defenses are too slow

The average phishing site is live for 21 hours before any blocklist catches it. During that window, users have no protection.

01

Blocklists lag behind attackers

Google Safe Browsing and similar tools rely on reported domains. A brand-new phishing site passes every check until someone reports it — which takes hours.

02

Typosquatting is trivially easy

Registering g00gle.xyz costs $1. Most users won't notice the difference until they've already entered their password.

03

Network-level tools can't see inside the browser

Firewalls and proxies inspect HTTP traffic. But a page that loads clean HTML and renders a phishing form via JavaScript is completely invisible to them.

04 — The white space

Nobody is analyzing domains at the moment of navigation

There is no tool that scores a domain's trustworthiness in real time, at the browser layer, using both AI and community signals — and acts on it automatically.

Where this fits

Modern security stacks protect the network and device layers. The browser — where actual work happens — has been the missing piece.

Features

What it does and why each feature was chosen

Every feature exists to close a specific gap. Nothing is decorative.

Auto-blocks dangerous domains

When you navigate to a domain that scores below the danger threshold, a full-screen overlay stops you before the page loads. It shows you the trust score, the AI's reasoning, and a list of specific risk signals. You can still proceed — but you do so knowingly.

Why: most phishing victims don't know they're on a fake site until after they've typed their password. Stopping navigation before interaction changes the outcome.

Warning banners for borderline sites

Sites that score in the caution range get an amber banner at the top of the page — non-intrusive, dismissible, but clearly visible. It auto-disappears after 10 seconds if you ignore it.

Why: not every suspicious domain should be blocked. A warning respects user autonomy while still surfacing the risk.

Detailed trust analysis in the popup

Click the shield icon on any tab to see the full breakdown: a trust score gauge, signal-by-signal scoring (brand similarity, TLD risk, entropy, subdomain abuse), and a plain-English AI explanation of why the domain was rated the way it was.

Why: a score without an explanation trains users to ignore it. Seeing "1 character away from paypal.com — likely typosquatting" builds intuition.

Right-click to analyze any link before clicking

Right-click any hyperlink → "Analyze link safety" — a toast appears with the domain's trust score and AI summary without navigating to the page.

Why: the riskiest moment is before the click, not after. This is proactive protection — the only feature that prevents the navigation entirely.

Community voting — Safe / Suspicious / Unsafe

Every user can vote on any domain. Votes are weighted by reviewer activity (more reviews = more weight, capped at 2×). Community consensus can escalate or de-escalate the AI's verdict — but only with a clear majority and minimum vote threshold.

Why: AI makes mistakes. A domain that launched yesterday may have no threat-feed history but be clearly phishing to anyone who looks at it. Human judgment fills that gap.

Report AI mistakes

If the AI gets a verdict wrong — flagging a legitimate site or missing a phishing one — you can report it directly from the popup with what the verdict should have been and why.

Why: no model is perfect at launch. Structured error reporting creates a feedback loop that makes the system more accurate over time.
How it works

Three signals, one score

Every domain gets scored on a 0–100 trust scale the moment you navigate to it. Three systems contribute to that score.

Heuristic engine

Fast, deterministic, explainable

Six signals scored and weighted: brand similarity (catches paypa1.com), digit substitution (catches g00gle), TLD risk (.xyz, .top, .buzz), Shannon entropy (catches randomly generated domains), subdomain abuse, and character patterns. Results in milliseconds, no AI needed.

AI — Llama 3.1 8B

Catches what rules miss

An LLM analyzes the domain name in context — understanding semantic tricks, unusual naming patterns, and combinations of signals that don't hit any single heuristic threshold. Returns a risk level, confidence score, and a plain-English explanation.

Community votes

Human judgment at scale

Weighted votes from real users. A clear majority (60%+) can escalate or de-escalate the AI's verdict. Active reviewers carry more weight. The system requires minimum 2 votes before community signal activates — preventing single-vote manipulation.

Combo overrides

Certain patterns always block

Digit substitution of a known brand (g00gle) combined with a high-risk TLD (.xyz) bypasses the weighted scoring entirely and forces a block — because no legitimate site uses that combination.

Community voting

AI is the starting point. Humans refine it.

The voting system exists because AI models make mistakes — especially on brand-new domains with no history. Community votes provide a correction layer.

STEP 1

You visit a domain

AI and heuristics produce an initial verdict

STEP 2

You cast a vote

Safe, Suspicious, or Unsafe from the popup

STEP 3

Vote is weighted

Active reviewers carry up to 2× weight

STEP 4

Consensus shifts the verdict

60%+ majority can escalate or de-escalate

⚖️
Weighted votes — New users start at 1× weight. Review 10+ domains: 1.5×. Review 50+: 2× (capped). Casual opinions carry less weight than engaged reviewers.
🔢
Minimum threshold — One vote does nothing. You need at least 2 votes before the community signal activates. This prevents single-user manipulation.
🔼
Unsafe majority escalates — 60%+ unsafe votes upgrades allow → warn, and warn → block. Community can push a site into a block even if AI missed it.
🔽
Safe majority de-escalates — 60%+ safe votes with 50%+ confidence downgrades block → warn. Community cannot fully clear a site — warn is the minimum floor.
🔄
Cache busts on every vote — Voting immediately invalidates the cached verdict. The next user to visit that domain gets a fresh analysis that reflects the new community data.

Install

Add to Chrome in 4 steps

The backend is already live. You only need the extension.

1

Clone the repo

git clone https://github.com/keertipc7/domain-authenticator.git

2

Open Chrome extensions

Go to chrome://extensions in your browser.

3

Enable Developer mode

Toggle Developer mode on — top right corner of the extensions page.

4

Load the extension

Click Load unpacked → select the extension/ folder. The shield icon appears in your toolbar immediately.

What's next

The roadmap

Features planned for future versions.

Next

Human verification for voting

CAPTCHA or proof-of-work before a vote counts — prevents automated vote stuffing and makes community signals more trustworthy.

Next

Auto-stop access on dangerous sites

Block form submissions and disable input fields on sites that score below threshold — not just warn, but actively prevent credential entry.

Next

Domain age signal

Newly registered domains (under 30 days) are the strongest phishing indicator. Integrating WHOIS data would add a high-confidence signal the heuristics currently miss.

Future

DOM-level credential form detection

Scan the rendered page — after JavaScript runs — for login forms on untrusted domains. Catches phishing pages that load clean HTML and render malicious content client-side.

Future

Policy engine integration

Expose the trust score as a policy signal — so enterprise admins can write rules like "if trust score < 40, isolate in remote browser" without any new infrastructure.

Future

Voter reputation system

Track voting accuracy over time — users who consistently vote in line with eventual AI consensus get higher weights. Users who vote against consensus lose weight.
